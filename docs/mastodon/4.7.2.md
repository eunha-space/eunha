Outstanding from 4.7.2
======================

Nothing. Signing HTTP Message Signatures with Ed25519 or ML-DSA keys remains
unimplemented, but so is it in Mastodon: local accounts' HTTP signatures are
RSA on both sides. Both algorithms are verified inbound.

4.7.2 changed no schema — `db/schema.rb` is byte-identical to 4.7.1's, and no
migration was added or touched — and no serializer, so `entities.json` is
unchanged. It is one security change and seven bug fixes, and eunha follows
each of them:

 -  **HEIF support disabled.** 4.7.2 takes `VipsForeignLoadHeif` off the list
    of libvips loaders it allows, so an image upload whose file is HEIC, HEIF
    or AVIF fails as it is processed, whatever type it was sent as, and
    `rescue Paperclip::Error` answers it with a 500 and
    `{"error":"Error processing thumbnail for uploaded media"}`. The three
    types are still in `MediaAttachment::IMAGE_MIME_TYPES`, so the instance
    entity still advertises them. Eunha refuses an image upload whose file is
    an ISO base media file with a HEIF or AVIF brand with the same status and
    body, on `/api/v1/media` and `/api/v2/media`, before the description is
    validated, as upstream's processing comes first; and it keeps advertising
    the types. Eunha never decoded them, and used to store such a file as
    sent, without a thumbnail or blurhash.

 -  **Relative privacy policy links in subscription emails** (#40486). The
    footer of `EmailSubscriptionMailer`'s mails linked `privacy_policy_path`,
    which goes nowhere in a mail. Eunha's linked `/about`, absolute; it now
    links `https://<domain>/privacy-policy`, the `privacy_policy_url` upstream
    links and the address the instance entity's `privacy_policy` gives.

 -  **Canonical email blocks interfering with freezing or approving users**
    (#40463). `UserEmailValidator` now runs only when the address is being
    changed, so saving a user for another reason no longer trips over a block
    added since it signed up. Eunha already checks the email blocks only when
    an account is created and when its address changes.

 -  **A non-custom-filter JSON import** (#40449 and #40451). `Form::Import`
    now refuses a JSON file for any type but custom filters as incompatible
    before reading it, and one with no filters as containing no data, and
    only then counts the rows. Eunha's import validation checks in that order
    with those messages.

 -  **Submitting a status twice** (#40439). The duplicate an
    `Idempotency-Key` names is now returned rather than lost, which upstream
    did with a 500. Eunha follows `PostStatusService#with_idempotency` as a
    whole: under `with_redis_lock("idempotency:lock:status:<account>:<key>")`,
    which a second request finds held and is answered 503, the key recorded
    as `idempotency:status:<account>:<key>` for an hour names what the first
    request created, a status or, since eunha now records it too, a scheduled
    status, looked up as this request would create it and 404 when it is
    gone. A scheduled status is answered with 200, as upstream's `render json:`
    does, where eunha answered 201.

 -  **`tootctl accounts create --reattach` and self-deleted accounts**
    (#40430). Reattaching now clears `requested_deletion_at` as well as
    `suspended_at`. `eunha accounts create --reattach` already cleared both.

 -  **Generated annual reports on account deletion** (#40394).
    `DeleteAccountService` now purges `generated_annual_reports`, which eunha
    does too. Comparing the rest of its `ASSOCIATIONS_ON_PURGE` found two
    eunha had missed: an account's tag follows, and its collections, which
    take their notifications with them. As `collections.account_id` has no
    `ON DELETE`, purging an account that owned a collection used to fail when
    it came to delete the account row.

 -  **Notifications after dismissing requests in bulk** (#40393).
    `dismiss_bulk` now removes the filtered notifications of every request it
    dismisses, as dismissing one did. Eunha's bulk dismissal always went
    through the single dismissal, which removes them.

The remaining change is the development `docker-compose.yml`, which eunha does
not have. All divergences were re-examined: none rests on a file 4.7.2 changed
in a way that alters the decision.
