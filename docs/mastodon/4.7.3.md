Outstanding from 4.7.3
======================

Nothing. Signing HTTP Message Signatures with Ed25519 or ML-DSA keys remains
unimplemented, but so is it in Mastodon: local accounts' HTTP signatures are
RSA on both sides. Both algorithms are verified inbound.

4.7.3 changed no schema — `db/schema.rb` is byte-identical to 4.7.2's, and no
migration was added or touched — and no serializer, so `entities.json` is
unchanged. Most of its fixes land on code eunha has, and eunha follows them:

 -  **Confirming a self-deletion** (#40576 and #40733). The deletion page now
    always asks for the username, and the password as well for an account
    that has one, and reads the username leniently: surrounding spaces and
    one leading `@` are dropped, case is ignored, and `username@domain` will
    do. Its title names the account. Eunha's `/account/delete` page, its
    `DELETE /api/v1/accounts` and the web client's settings page all ask the
    same, and read it the same.

 -  **Reported posts on account deletion** (#40650). `DeleteAccountService`
    keeps the posts of open reports for the moderators, as before, but now
    discards them, so nobody else sees them. So does eunha.

 -  **Link previews on account deletion** (#40624). `PreviewCardsStatus` rows
    have no foreign key, so `BatchedRemoveStatusService` now deletes those of
    the posts it removes. So does eunha.

 -  **Image descriptions on account deletion** (#40621). The avatar's and
    header's descriptions are now cleared with the images. Eunha always
    cleared them.

 -  **Featured collections on account deletion** (#40623). `collection_items`
    joined `ASSOCIATIONS_ON_PURGE`: a deleted account leaves the collections
    that featured it, each counting one item fewer. Eunha does the same, which
    also lets an account featured somewhere be deleted outright, as
    `collection_items.account_id` has no `ON DELETE`.

 -  **Suspended accounts deleted by moderators** (#40645).
    `Admin::AccountDeletionWorker` passes the suspension on, so an account
    whose data a moderator deleted, or whose thirty days ran out, stays
    suspended, locally, rather than being marked as deleted by its owner.
    Eunha's admin deletion and its scheduled one do the same.

 -  **Logging account data removal** (#40572). Deleting a suspended account's
    data from the admin is now in the audit log, as `destroy` on the account,
    “deleted account data for”. Eunha's `DELETE /api/v1/admin/accounts/:id`
    logs it and its audit log words it so.

 -  **Warning moderators of higher position** (#40646). `process_strike!`
    asks `AccountPolicy#warn?`, so a plain warning, disabling a login, and
    deleting or marking sensitive a report's posts need a role above the
    account's. Eunha asks it at the same point. Refused, eunha's action
    changes nothing, where upstream keeps the posts it had already marked
    sensitive (`refused-strike-keeps-nothing` in
    [divergences](./divergences.md)).

 -  **Rate limits and e-mail addresses** (#40658). The throttles that count
    per address — password resets, confirmations, setup, sign-ins — count it
    canonicalized, so dots and a `+tag` no longer make another address.
    Eunha's do the same.

 -  **Doorkeeper 5.9.9** (#40716, from 5.9.6). What changed that a client can
    see: a token sent more than one way at once — the `Authorization`
    header, an `access_token` or `bearer_token` parameter, the query and the
    body counting apart — is no token at all (5.9.7); a body that cannot be
    parsed carries none (5.9.8); and denying an authorization checks the
    client and its redirect URI first, and shows a refusal rather than
    sending it anywhere (5.9.9). Eunha now reads a token from those
    parameters as well as the header, which it did not before, and refuses
    one sent more than one way, though not from a multipart body
    (`token-not-read-from-multipart`). Its deny already refused a redirect
    URI the client had not registered, which was a divergence and is now
    upstream's behaviour too; it now also answers a missing `client_id`
    with 400. Script-scheme redirect URIs and unregistered response types,
    the rest of 5.9.9, eunha already refused. `AuthorizedApplicationsController`
    answering 401 without a resource owner concerns a page eunha does not
    serve.

 -  **Malformed WebFinger subjects** (#40731). `ProcessAccountService` raises
    a proper error for a subject missing its username or its domain, where it
    used to fail on the missing half. Eunha, through ojak's WebFinger
    confirmation, already refused such a subject, and keeps the actor out.

 -  **An invalid date of birth at sign-up** (#40607). Mastodon's sign-up form
    sends the date as three fields, and an impossible one, such as the 31st
    of February, raised a server error; it is now refused as invalid.
    Eunha's form sends one date, and an impossible one is refused as
    missing, as upstream's API refuses it, with no server error to fix.

 -  **`POST /api/v1/accounts` with `SSO_ACCOUNT_SIGN_UP`** (#40681). Sign-up
    through the API is now refused when sign-ups go through an external
    provider. Eunha has no external sign-in providers, so it has nothing to
    refuse.

The rest is not eunha's to follow. The thread view's reply order (#40481) is
the web client's own bookkeeping, which eunha's client does not do: it shows
the order the context API gives. The mail footer's spacing (#40440) is
Mastodon's stylesheet, which eunha's mails do not use. The 404 page's link
home (#40369) is Mastodon's error layout; eunha's web client answers an
unknown path with its home page. The picture-in-picture player's z-index
(#40484), the profile editor's padding (#40700), the onboarding's “Next step”
button (#40634), the landing page's description (#40272) and the quotes
list's disclaimer (#40587) are in parts of Mastodon's web UI eunha's client
does not have; nor does it have the confirmation before leaving a post
unsent that #40478 restores. The rest are dependency updates (aws-sdk-s3,
rack-proxy, Yarn, FFmpeg), CI, translations and the version bump.

All divergences were re-examined. `oauth-deny-checks-the-redirect-uri` is
gone, as Doorkeeper 5.9.9 does what it recorded; `account-deletion-rest-api`
now describes the username challenge; two are new,
`refused-strike-keeps-nothing` and `token-not-read-from-multipart`. None of the
others rests on a file 4.7.3 changed in a way that alters the decision.
